- q35_0.8b: mstar-pr was measured after the other arms (its final sha landed mid-run), so it is not interleaved in time with them; the node is dedicated (no co-tenants) and load averages are logged per cell. From q35_9b on, every arm including mstar-pr is interleaved with the per-round rotation.
- mstar has no chunked prefill on the Qwen3.5 path; vLLM and SGLang keep theirs (at their tuned budget). Long-prompt TTFT under load is therefore not a like-for-like scheduler comparison.
- mstar's chat API reports usage as zeros, so its per-request output length is the forced max_tokens (ignore_eos); vLLM/SGLang are checked against their own usage.completion_tokens (a mismatch fails the request). For mstar the re-tokenized streamed text length is recorded (retok_ratio) as an audit.
- No speculative decoding (MTP) on any arm in the main tables. vLLM's and SGLang's Qwen3.5 recipes offer MTP for latency, so each model has a clearly labelled supplementary table with each competitor's recipe MTP setting at c = 1, 4, 16 (same GSM8K/parity gate on that server). mstar has no MTP path for Qwen3.5 here.
- Scope: Qwen3.5 text on node8 (this report). Diffusion and TTS run on a second node with their own report (REPORT_DIFFUSION.md); Qwen3.5 image/video and Qwen3-Omni are not benchmarked here yet (engines and weights are staged, workloads are not built).
- Competitor tuning used one short sweep (random 1024/256, c = 1/32/128, one server per knob set, a single process each); differences between knob sets were mostly within ~5%, i.e. near the cross-process noise, so the chosen set is "best observed", not "significantly best".
- vLLM `--language-model-only` and SGLang `--language-only` (when chosen) skip the vision tower; they are text-only settings and are not used for multimodal workloads. mstar always loads its vision encoder (colocated) in these configs.
- mstar restarts are not uniformly warm: some restarts recompiled/autotuned part of the graph (startup 100-340 s vs a 1500 s cold start), so kernel selection can differ between rounds (benchmarking skill trap 1); the min-max across rounds shows how much that moves the numbers.
- GSM8K has a binomial sd of about 0.03 at n=250, and greedy answers differ across server processes of the same engine (vLLM 0.524 vs 0.532 in two processes), so accuracy differences under ~0.03 are not meaningful.
- SGLang + MTP at --mem-fraction-static 0.85 ran out of GPU memory at c=128 (CUDA graph capture/allocation under spec decoding); the MTP supplement therefore uses 0.75 for SGLang and only c = 1/4/16 (the 0.85 rows are discarded).
- M* HTTP frontend: tuned like a competitor knob (Python uvicorn vs the Rust mstar-server). On q35_0.8b the Rust frontend passed the gate but its geomean was only +2.4% (c=1 -12%, c=128 +21%), under the +3% rule fixed beforehand, so Python stays for that model; the rule is re-applied per model.
- q35_0.8b random_1024_256 at c=16: both M* arms show a throughput dip and TTFT p99 ~2.5 s in every round (not at c=8 or c=32); not yet explained (profile pending at that point).
- Rounds are resumable at the cell level: after a runner restart, a round's remaining cells run on a fresh server process, so a few rounds may span two processes (recorded in startup.jsonl / servers/).
- Vision (q35_*_vl): inputs are normalised client-side so no engine resizes or resamples them: MMMU-val images fit in 896x896 with sides rounded down to multiples of 224 (lcm of SGLang's 28 px and HF/vLLM/M*'s 32 px factors); videos are Video-MME "short" clips of 8/30/60 s re-encoded at exactly 2 fps (every engine's Qwen3-VL default) and 448x224 (16/60/120 frames, under every engine's per-frame and total pixel limits). vLLM runs with `--mm-processor-cache-gb 0`, SGLang with `SGLANG_VLM_CACHE_SIZE_MB=0`, so repeated media can't skip preprocessing or the encoder. Vision competitors are tuned again without the text-only knobs.
- Vision gate (fixed before the run): image parity (gate.py on 8 MMMU prompts vs transformers) must pass, video parity must pass where the transformers video oracle runs (else recorded as UNCHECKED), and MMMU-200 accuracy >= min(vLLM, SGLang) - 0.05.
- Qwen3-Omni: all three engines on 2 GPUs (M*'s shipped qwen3omni_2gpu.yaml; vllm-omni's and sglang-omni's default speech deploy configs, thinker GPU 0 / talker GPU 1), each competitor at its recommended default (no knob sweep). Text-out workloads (ShareGPT T2T, LibriSpeech test-clean A2T) use real EOS with a 256-token cap and count actual output tokens; T2S uses the repo's benchmark.runner adapters (audio-s/s, TTFA, RTF). The Omni gate: GSM8K >= min(competitors) - 0.03, A2T WER <= min + 1 pt, T2S Whisper WER (speech vs the engine's own text) <= min + 2 pt with no silent WAV. M* stays on the Python frontend for Omni (the Rust frontend's speech path is unverified here).
- vllm-omni 0.30.0 ships without vLLM; its venv gets vllm==0.30.0 (the release it is built on) in a setup step.
